# Agent Harness 战略备忘录

> 本文整理自一次关于专业 agent、harness 技术、长尾任务地图、软件迁移场景和商业化可能性的讨论。
>
> 核心问题：作为软件工程师，是否可以通过掌握 OpenClaw、Hermes 等 agent harness 技术形成竞争壁垒？

## 1. 核心结论

单纯掌握 OpenClaw、Hermes 或某个 agent 框架的全部 harness 技术，**可以形成阶段性优势，但不足以形成长期壁垒**。

真正的壁垒不在于“会用某个 agent 框架”，而在于：

> 能否把通用 agent 能力，转化为某个专属高价值场景中的稳定交付能力。

更完整的公式是：

> **软件工程经验 × agent harness 实战 × 长程任务方法论 × 专属场景 × 评测体系 × 内容传播 × 可交付产品**

其中最关键的是：

1. 不追求解决所有问题。
2. 聚焦一个主打场景。
3. 持续优化成功率、成本、速度和可验证性。
4. 用真实任务清单、token 成本、失败案例和评测数据建立信任。

## 2. 不要做通用 agent，要做专业 operating layer

未来很多专业 agent 未必是从零开发一个新 agent，而是在强通用 agent 之上叠加：

- skills
- 私有数据
- 专用工具
- 任务流程
- 领域约束
- eval / benchmark
- 人类验收机制
- 失败恢复机制
- 成本统计和风险报告

因此更合理的定位不是：

> 我要开发一个新的通用 agent。

而是：

> 我要开发一个让通用 agent 在特定场景稳定交付的专业能力包。

也可以称为：

> **专业场景的 agent operating layer**

或者：

> **通用 agent 之上的专业化封装层。**

通用 agent 提供基础能力：理解任务、读代码、改文件、执行命令、调用工具、多轮修复、使用上下文。

专业层真正需要补齐的是：

- 任务拆解方式
- 上下文装配策略
- 外部状态管理
- 测试驱动验证
- worktree 隔离
- 失败归因
- 可复现 benchmark
- 可交付报告
- 适合某类任务的 workflow

## 3. 竞争壁垒来自专属场景

不能指望 agent 解决所有问题。真正可行的策略是：

> 在一个高价值长尾场景中，持续把 agent 的成功率、成本、速度和可验证性优化到领先水平。

通用 agent 会不断变强，但它们很难天然覆盖所有垂直场景的最后一公里。个人或小团队的机会在于：

1. 选择一个足够窄但足够痛的场景。
2. 把任务拆成长期可评测的长尾任务清单。
3. 每次执行后记录模型、harness、token、时间、人工介入、成功率和失败原因。
4. 基于失败原因持续优化 harness。
5. 把方法论沉淀成文档、工具、内容、课程或服务。

推荐主打场景：

> **AI 辅助软件迁移 / 代码现代化 / 依赖替换 / 测试补齐。**

这个场景适合软件工程师切入，因为它具备几个特点：

- 不是简单 prompt 能解决。
- 有明确验收标准。
- 可以通过测试验证结果。
- 容易形成案例库。
- 有真实商业需求。
- 需要工程流程、状态管理和失败恢复。
- 可以内容化和产品化。

## 4. 类似 Tesla 机器人的长尾任务清单

一个重要想法是：为 agent 建立类似 Tesla 机器人长尾任务清单的能力地图。

不要抽象地说 agent 很强，而是明确记录：

> 在什么模型、什么 harness、多少 token、多少时间、多少人工介入下，它到底能完成哪些真实任务。

这可以形成：

> **Agent Long-Tail Task Map**

也可以叫：

- Agent Capability Map
- Long-Tail Agent Benchmark
- HarnessEval
- AgentOps Task Matrix
- 智能体长尾任务地图
- Agent 能力边界清单
- Harness 任务评测矩阵
- AI 工程智能体任务图谱

### 示例任务矩阵

| 级别 | 任务类型 | 示例任务 | 壁垒强度 | 说明 |
|---|---|---|---|---|
| L1 | 单步任务 | 解释代码、生成脚本、修复简单 bug | 弱 | 很快会被模型原生能力覆盖 |
| L2 | 短程闭环任务 | 修改代码并运行测试 | 中 | 需要 observe → fix → test 循环 |
| L3 | 中程工程任务 | 迁移一个函数、类、模块 | 较强 | 需要任务拆解、状态管理、失败归因 |
| L4 | 长程项目任务 | 迁移一个 crate/package | 强 | 需要外部状态、checkpoint、测试基线 |
| L5 | 自治型产品任务 | 长期维护项目、处理 issue、生成 PR | 很强 | 需要权限、安全、评测、成本控制 |

真正的机会在 L3-L5。

L1-L2 很容易被通用模型和通用 agent 吞掉；L3-L5 更需要专业 harness、领域流程和工程经验。

## 5. 软件迁移场景的任务地图

可以围绕软件迁移建立任务清单：

| 任务 | 示例 | 是否适合作为主打 |
|---|---|---|
| 修复单文件 bug | 修一个明确的 Python bug | 太普通，壁垒弱 |
| 为模块补测试 | 给旧模块补单元测试 | 适合作为基础能力 |
| 迁移函数/类 | Rust 函数迁移到 Python | 适合 |
| 迁移模块 | 一个 crate 内部模块迁移 | 很适合 |
| 迁移 package/crate | Rust crate → Python package | 非常适合 |
| 依赖替换 | 老库替换成新库 | 高价值 |
| 项目现代化 | 老项目迁移到新技术栈 | 高价值但复杂 |
| 多 agent 并行迁移大型 repo | 多 worktree + 多 thread | 长期护城河 |

## 6. 需要记录的评测指标

每个任务都应该记录：

- 任务描述
- 输入 repo / commit
- 目标变更
- 使用模型
- 使用 agent / harness
- token 消耗
- 运行时间
- 人工介入次数
- 测试是否通过
- 编译是否通过
- 是否保持 API 兼容
- 是否生成风险报告
- 是否可复现
- 失败原因
- 改进后的下一轮结果

核心不是一次 demo 成功，而是持续积累：

> 第一次：agent 能完成，但需要大量人工介入。  
> 第二次：发现失败原因，改进任务拆解。  
> 第三次：加入自动测试和状态文件。  
> 第四次：加入 worktree 并行和回滚。  
> 第五次：加入 benchmark 和 token 统计。  
> 第十次：已经比别人更清楚这类任务的真实边界。

## 7. 为什么有人愿意付费

软件迁移、代码现代化、遗留系统改造是现实存在的付费场景。

客户真正关心的不是“agent 很酷”，而是：

> 能否降低迁移旧代码的时间、风险和人力成本。

可能的付费场景包括：

| 服务包 | 客户痛点 | 交付物 | 付费意愿 |
|---|---|---|---|
| 小型 repo 现代化 | 项目旧、没人维护 | 可运行新版本 + 测试 | 中 |
| 依赖替换 | 老库废弃、安全风险 | 替换方案 + PR | 中高 |
| 代码翻译 | 想换语言或框架 | 迁移代码 + 差异报告 | 中 |
| 测试补齐 | 不敢改老代码 | 单元测试 + 回归测试 | 高 |
| Migration audit | 不知道能不能迁 | 迁移评估报告 | 高 |

更适合个人起步的客户不是大型银行、保险或政府核心系统，而是：

- 中小团队
- 开源项目
- 独立开发者
- 技术团队内部的老项目
- 需要快速验证迁移可行性的团队

起步时不要说：

> 我提供通用 AI 代码迁移 agent。

更可信的说法是：

> 我专门做可测试的软件迁移任务，用 agent harness 降低迁移成本，并给出 token、成功率、失败点和验收报告。

## 8. 产品形态不是 agent，而是 skill + harness + eval

真正要开发的可能不是一个完整 agent，而是：

> **Agent Skill Pack for Software Migration**

或者：

> **AI Code Migration Harness**

它不是替代 Codex、Claude Code、OpenClaw 或 Hermes，而是增强它们。

它的价值主张是：

> 让通用 coding agent 在代码迁移任务上更稳定、更可控、更可验证。

可能包含：

- 迁移任务模板
- repo 分析脚本
- task tree 生成器
- worktree 管理脚本
- 测试基线工具
- agent 指令模板
- 失败归因模板
- token 成本统计
- migration report 模板
- benchmark 任务集
- PR review 模板

## 9. 内容闭环

这个方向天然适合形成内容闭环：

1. 选择真实迁移任务。
2. 让 agent 执行。
3. 记录 token、耗时、失败点和人工介入。
4. 复盘 harness 如何优化。
5. 生成文章、视频和开源文档。
6. 沉淀成工具、课程、咨询或服务。

可做内容主题：

- 我用 agent 迁移一个真实开源项目
- 为什么 AI 迁移代码会失败
- 如何用 worktree + task tree + tests 控制 coding agent
- 一个 crate 迁移任务到底消耗多少 token
- AI 代码迁移成功率报告
- 通用 agent 之上如何构建专业 skill pack
- 为什么专业 agent 不一定要从零开发

## 10. 战略宣言

可以把整体战略浓缩成：

> 我们不幻想解决所有问题，而是在一个高价值长尾场景中，持续把 agent 的成功率、成本、速度和可验证性优化到领先水平。通过任务清单、评测数据和专属 harness，形成可交付、可传播、可产品化的竞争壁垒。

更短的版本：

> 通用 agent 是大脑；我们的壁垒是让它在软件迁移这个场景中稳定交付。

或者：

> 不做通用 agent，做专业场景的 agent operating layer。

## 11. 下一步行动

最小可行版本可以不是复杂代码，而是一组可复现文档和脚本：

```text
README.md
notes/agent-harness-strategy.md
benchmarks/tasks.yaml
templates/migration-report.md
templates/failure-postmortem.md
prompts/migration-plan.prompt.md
scripts/create-worktree.sh
scripts/run-tests.sh
scripts/collect-metrics.sh
```

第一阶段目标：

1. 选一个小型开源 repo 或 crate。
2. 定义迁移目标。
3. 建立测试基线。
4. 用通用 coding agent 执行迁移。
5. 记录 token、时间、失败点和人工介入。
6. 输出第一份 migration report。
7. 根据失败原因改进 harness。
8. 把全过程写成公开文档和视频脚本。

## 12. 最重要的提醒

不要把护城河建立在某个具体框架上。

OpenClaw、Hermes、Codex、Claude Code 都可能变化，也可能被更强的通用 agent 替代。

更稳的护城河是：

> 我知道如何让任何强通用 agent，在软件迁移这个场景中稳定交付结果。

这才是长期价值。
