# 从封闭生态系统到自主源代码迁移

> 日期：2026-08-07  
> 主题：封闭生态系统、OpenAI Five / AlphaZero、自主学习闭环、LLM + Verifier + Search，以及这些思想如何迁移到源代码迁移工程。

这篇笔记整理了今天的一整条讨论链路。讨论从一个自然系统问题开始：**地球生物圈中是否存在能够从整体中相对独立出来的子系统？** 随后逐步连接到生物圈 2 号、OpenAI Five、AlphaZero、强化学习、大模型、自动验证、系统创新，最后落到一个非常具体的软件工程问题：**如何构造一个能够让 Coding Agent 自主完成大规模源代码迁移的封闭训练环境。**

整条讨论最终收敛到一个核心认识：

> 真正稀缺的未必是某一个更强的模型或某一个全新的算法，而是把模型、环境、验证器、搜索、记忆、测试、反馈等既有能力组织成一个能够自我增强的闭环系统。

---

## 一、自然界是否存在相对封闭、能够独立运行的生态子系统

最初的问题是：

> 在地球的整个生物系统中，是否有一些相对封闭的子系统能够从整体中独立出来？

答案是肯定的，但自然界中的“独立”通常不是绝对隔绝，而是**高度相对独立**。

可以把生态系统理解成一个连续谱：

```text
开放生态系统
    ↓
半封闭生态系统
    ↓
高度封闭生态系统
    ↓
理论上的完全封闭系统
```

自然界通常只能达到第三层。典型案例包括：

- 深层洞穴生态系统；
- 深层地下微生物生态系统；
- 深海热液喷口生态系统；
- 地下湖与冰下湖；
- 在种群交流意义上相对封闭的岛屿生态系统。

其中最值得关注的，并不是空间上是否完全封闭，而是**内部功能是否形成闭环**。

一个相对独立的生态系统往往至少包含：

```text
外部能量
   ↓
生产者
   ↓
消费者
   ↓
死亡 / 排泄
   ↓
分解者
   ↓
无机物
   └────────→ 再次进入生产环节
```

这说明一个重要问题：

> 一个系统不需要与外界完全断绝联系，才可以拥有高度自治性。

整个地球生物圈本身也持续接受太阳能，并把热量辐射到宇宙。因此真正能够高度循环的是**物质**，而能量通常必须持续流过系统。

由此可以给“相对独立生态系统”一个更准确的系统论定义：

> 一个内部拥有足够完整的物质循环、能量转换和自我调节机制，使外界主要提供边界条件和少量输入，而不需要持续参与内部组织过程的系统。

这与“生物圈 2 号作为未来软件工程形态的类比”产生了直接联系。

真正值得类比的，不是完全封闭，而是：

> **切出一个边界足够清晰的局部世界，使内部形成生产、消耗、回收、反馈、自我修复和自我调节的完整回路。**

未来的软件工程系统仍然需要外部提供：

```text
需求
算力
基础模型
外部 API
```

但系统内部可以逐渐自行完成：

```text
需求
 ↓
设计
 ↓
编码
 ↓
运行
 ↓
测试
 ↓
发现缺陷
 ↓
修改
 ↓
重新验证
 ↓
部署
 ↓
运行反馈
 └────────────→ 新一轮修改
```

因此更准确的类比并不是“绝对封闭的软件世界”，而是：

> **高度自治的半封闭系统（semi-closed autonomous system）。**

自然界中还存在一个非常重要的嵌套现象：

```text
细胞 ⊂ 器官 ⊂ 个体 ⊂ 种群 ⊂ 局部生态系统 ⊂ 生物圈
```

每一层都没有完全从上一层脱离，但都通过“边界 + 内循环 + 反馈”获得了相对自治性。

## 二、从封闭生态系统联想到 AlphaZero 与 OpenAI Five

接下来出现了一个关键联想：DeepMind 和 OpenAI 都做过类似实验——让人工智能系统在缺少人类专家策略数据的情况下，在复杂游戏环境中进行自主学习，最后达到极高水平。

这里最重要的不是游戏本身，而是这种实验背后的结构：

> **不是单纯调用一个智能模型，而是把智能体放入一个可以持续行动、持续得到反馈、持续修正自身策略的环境中。**

最初可以把它理解成：

> 大模型 + 强化学习。

但继续抽象以后，会发现更本质的结构其实是：

> **强大的先验模型 + 封闭可交互环境 + 自动验证器 + 持续搜索/学习机制。**

可以表示为：

```text
              ┌──────────────┐
              │   智能模型    │
              └──────┬───────┘
                     │
                生成行动/策略
                     ↓
┌────────────────────────────────────┐
│           可执行环境               │
│                                    │
│   状态 → 行动 → 新状态 → 结果      │
└──────────────────┬─────────────────┘
                   │
                   ↓
              自动验证 / 评分
                   │
          ┌────────┴────────┐
          ↓                 ↓
        成功               失败
          │                 │
          └───────┬─────────┘
                  ↓
             搜索 / 学习
                  │
                  └────────→ 再次行动
```

强化学习只是实现“根据反馈改进策略”的方法之一。

其他方法同样可以承担这一角色，例如：

- evolutionary search；
- beam search；
- best-of-N；
- verifier-guided search；
- policy optimization；
- 经验重放；
- curriculum learning。

因此比“LLM + RL”更稳定的抽象是：

> **Generator + Environment + Verifier + Search/Learning。**

---

## 三、真正重要的是“知识开始在闭环里自己增长”

传统大模型的知识链条更像：

```text
人类知识
   ↓
训练数据
   ↓
LLM
   ↓
回答
```

这种结构中，主要知识增长发生在模型训练阶段。

AlphaZero / OpenAI Five 一类系统则不同：

```text
初始策略
   ↓
尝试
   ↓
环境
   ↓
反馈
   ↓
改进策略
   ↓
产生更高级经验
   ↓
更强策略
   ↓
面对更强对手 / 更难状态
   ↓
……
```

这里出现了能力飞轮：

> **能力提高 → 产生更困难、更高质量的经验 → 学习更高级策略 → 能力再次提高。**

这与普通 Coding Agent 的一次性使用有很大区别。

普通模式通常是：

```text
Codex
 ↓
完成任务
 ↓
用户验收
 ↓
结束
```

下一次任务并不会天然因为上一次任务而获得一个更强的项目级策略。

理想的闭环应该变成：

```text
Coding Agent
 ↓
解决任务
 ↓
测试 / benchmark / runtime
 ↓
发现错误
 ↓
重新修改
 ↓
通过
 ↓
经验沉淀
 ↓
形成更强测试和更困难任务
 ↓
再次解决
 ↓
……
```

于是失败和成功都不再是一次性事件，而成为下一轮系统能力的输入。

---

## 四、为什么 OpenAI 强大：单点创新之外，还有“方法的组织能力”

讨论进一步扩展到一个更宏观的判断：

> OpenAI、DeepMind 等领先机构的优势，不只是不断做出单个重大突破，而是长期进行大量 AI 实验和创新项目，并把这些实验产生的方法重新组织起来。

很多单独技术并不神奇：

- 预训练；
- reinforcement learning；
- verifier；
- tool use；
- memory；
- agent loop；
- sandbox / worktree；
- eval；
- synthetic data；
- self-play；
- adversarial search；
- tracing；
- regression tests。

但是这些能力一旦形成正确连接：

```text
更强模型
   ↓
能解决更复杂任务
   ↓
产生更高质量 trace
   ↓
eval 发现新的失败模式
   ↓
失败转化为训练数据 / verifier / regression case
   ↓
RL / search / optimization
   ↓
模型或策略进一步增强
   ↓
能够进入更复杂环境
   ↓
……
```

系统能力就不再是局部能力的简单相加，而会出现**涌现式增强**。

这可以凝练为一个重要的方法论：

> **很多时候，人类缺少的并不是新的方法，而是发现既有方法之间尚未建立的连接。真正高阶的创新，是把分散的局部能力组织成能够自我增强的闭环系统。**

因此，值得长期研究的问题不仅是：

> “某项 AI 技术是什么？”

而是：

> **“能力究竟是如何被组织出来的？”**

这也是为什么 AlphaZero、生物圈、Agent、软件工程闭环、Opik、自动验证、定向构造能力等表面上不同的问题，实际上可以被统一到一个更深层的系统问题中：

> **如何设计一个边界清晰、反馈可靠、局部模块彼此连接，并能够通过循环不断产生更高层次能力的系统。**

## 五、OpenAI Five 的基本原理

回到 Dota 2。

OpenAI Five 是一个非常典型的“大规模强化学习 + self-play + 可持续训练基础设施”的实验，而不是大语言模型玩游戏。

它的大致训练循环可以理解为：

```text
随机初始化策略
      ↓
5 个 AI 组成一队
      ↓
与另一支 AI 队伍比赛
      ↓
      Dota 2
      ↓
获得奖励 / 惩罚
      ↓
PPO 更新策略网络
      ↓
得到更强版本
      ↓
再与当前 / 历史版本比赛
      ↓
      ……
```

它没有把“人类高手怎么玩”直接作为主要学习来源，而是通过 self-play 形成自己的训练数据。

需要准确区分的是：这并不是“什么先验知识都没有”。

系统仍然由人类设计了：

- observation；
- action space；
- reward；
- reward shaping；
- 游戏接口；
- 训练基础设施；
- 对手采样机制；
- 允许使用的游戏机制范围。

因此更准确的说法是：

> **没有依赖人类专家策略进行模仿，但拥有一个由人类精心设计的学习世界。**

这个区别非常重要。

---

## 六、OpenAI Five 最重要的机制：Self-play

Self-play 的美妙之处在于：

```text
弱 AI
  ↓
与弱 AI 对战
  ↓
找到能够获胜的新策略
  ↓
变成更强 AI
  ↓
对手也随之变强
  ↓
旧策略失效
  ↓
必须发明更好的策略
  ↓
再次变强
  ↓
……
```

传统训练系统需要人类持续设计：

```text
Level 1
Level 2
Level 3
...
Level 10000
```

而 self-play 的关键是：

> **智能体自己就是课程生成器（curriculum generator）。**

能力越强，它面对的训练环境就越难。

这导致训练分布不会永久固定在某个静态数据集上，而可以随能力增长不断变化。

OpenAI Five 最终在 2019 年以 2:0 击败当时的 Dota 2 世界冠军 OG，并在公开 Arena 中达到极高胜率，说明这样的大规模 self-play 机制在复杂、长期、部分可观测、多智能体环境中确实能够产生世界级策略。

但它没有“解决完整 Dota 2”。最终系统仍运行在经过工程化裁剪的游戏子空间中，英雄池和部分机制有限制。

这个事实反而很有启发：

> **不需要一开始就把整个真实世界完整建模；可以先构造一个足够复杂、但仍然可控和可验证的子世界，再逐渐扩大边界。**

---

## 七、OpenAI Five 是否开源

OpenAI Five 没有以“可以直接完整复现实验”的形式全部开源。

公开程度很高的主要是：

- 论文；
- 训练方法；
- 网络结构；
- 大量超参数；
- reward 设计；
- self-play 机制；
- ablation；
- 比赛 replay 和研究结果。

但完整的大规模训练基础设施、Dota 集成、最终训练 pipeline 等并没有作为一个端到端可直接运行的官方项目完整开放。

因此可以概括为：

> **研究方法高度公开，但完整生产级训练系统没有整体开源。**

---

## 八、OpenAI Five 对今天 Coding Agent 的真正启发

OpenAI Five 展示的深层结构不是“PPO 很强”，而是：

```text
             智能体
               ↓
          可执行的世界
               ↓
          大规模自主尝试
               ↓
          自动产生反馈
               ↓
            学习 / 搜索
               ↓
          更强的智能体
               ↓
        更困难的环境 / 对手
               ↓
              ……
```

今天 Coding Agent 有一个 OpenAI Five 当年没有的巨大优势：

> **LLM 已经拥有极其强大的人类知识先验。**

它已经知道：

- 编程语言；
- 编译器；
- 操作系统；
- 数据结构与算法；
- 常见架构；
- API；
- debugging；
- testing；
- Git；
- Linux 工具；
- 大量软件工程模式。

因此今天可能采用的是：

```text
强大的预训练 LLM
        +
相对少量但高质量的定向搜索
        +
可靠环境反馈
        +
持续经验积累
```

而不是：

```text
几乎没有先验
        +
巨大随机搜索
```

这与此前形成的“大模型定向构造能力”定义高度吻合：

```text
目标
 ↓
从目标反推需要的结构
 ↓
生成高概率候选
 ↓
真实环境验证
 ↓
失败反馈
 ↓
修改候选 / 搜索方向
 ↓
再次生成
 ↓
收敛
```

因此 LLM 可以被理解成：

> **巨大搜索空间中的强启发式策略生成器。**

而环境、verifier、search / RL / evolution 则负责施加持续的选择压力。

# 九、如何把 OpenAI Five / AlphaZero 思路迁移到源代码迁移项目

这是整个讨论最后的工程落点。

源代码迁移非常适合这种范式，因为它天然具有：

- 明确的目标状态；
- 可复制的环境；
- 可执行的动作；
- 可自动化验证的结果；
- 极低的失败成本；
- 可以通过 Git / worktree 随时 reset；
- 可以积累大量真实 trajectory。

因此可以把“源代码迁移”重新定义为一个 AI 可以不断玩的**单人游戏**。

---

## 十、Dota 2 与源代码迁移的对应关系

| Dota 2 | 源代码迁移 |
|---|---|
| 游戏世界 | 原项目 + 目标项目 |
| 当前局面 | 当前 repository 状态 |
| Agent | Coding Agent |
| Action | 修改代码、运行命令、调整配置 |
| 游戏规则 | 编译器、语言语义、API、架构约束 |
| Reward | build、tests、差分结果、性能、静态检查 |
| 输 | 编译失败、测试失败、行为不一致 |
| 赢 | 当前迁移任务完整通过验收 |
| Replay | trace + commit + test results |
| 新开一局 | reset worktree |
| 难度提升 | 从简单模块迁移到复杂模块 |
| 历史策略 | 历史成功迁移案例与经验 |

于是原来的任务：

> 把一个大型项目从 A 技术栈迁移到 B 技术栈。

可以重新描述为：

> **让 Agent 在一个可自动判分的软件世界中不断采取行动，直到 repository 达到目标状态。**

---

## 十一、不要一开始把整个仓库当成一局游戏

大型迁移如果只有一个最终目标：

```text
输入：100 万行旧代码
目标：全部迁移
Agent：开始
```

反馈距离会非常长。

Agent 修改几百个文件以后才发现最终结果错误，很难判断根因。

因此应当按模块建立大量局部闭环：

```text
整个项目

├── module A
│     ├── migration task A1
│     ├── migration task A2
│     └── migration task A3
│
├── module B
│     ├── migration task B1
│     └── migration task B2
│
└── module C
      ...
```

每一个 migration task 都必须具备：

```text
输入状态
   ↓
Agent 修改
   ↓
自动验证
   ↓
成功 / 失败
```

这与此前已经形成的迁移策略完全一致：

> **以 module 为单位迁移 → 大量 E2E / 差分验证 → 最终人工验收。**

现在只是进一步把它升级成一个可自主探索的 AI 环境。

---

## 十二、最关键的不是 RL，而是 Verifier

如果只从工程优先级看，第一步不是训练模型，而是回答一个问题：

> **怎样自动判断新实现是否真的等价于旧实现？**

对于源代码迁移，最重要的基础设施之一是 Differential Verifier。

```text
                 input
                /     \
               ↓       ↓
          Original    Migrated
           System      System
               ↓       ↓
            output    output
                \      /
                 ↓    ↓
                 compare
                    ↓
             same / different
```

例如：

```text
input.json
    ↓
旧程序
    ↓
old-output.json

input.json
    ↓
新程序
    ↓
new-output.json

old-output ≈ new-output ?
```

只要这个比较足够可靠，就拥有了软件迁移世界里的“胜负判定器”。

这是整个闭环中最重要的资产之一。

---

## 十三、Reward 不应该只有通过 / 失败

如果奖励只有：

```text
整个项目迁移成功：+1
迁移失败：0
```

反馈会过于稀疏。

应当设计多层次 reward / score，例如：

```text
代码能解析                   +1
编译成功                     +5
单元测试通过                 +10
接口契约一致                 +20
差分测试 90% 一致            +40
所有 E2E 通过                +100
性能不退化                   +20
没有违反架构约束             +20
```

以及负反馈：

```text
编译错误                      -5
新增 warning                  -2
行为发生变化                 -20
破坏其他模块                 -30
性能严重退化                 -20
引入架构违规                 -20
```

这样 Agent 得到的就不是简单的：

> 失败。

而是：

> 当前 candidate 从 43 分提升到了 78 分，但性能和某个 edge case 仍然有问题。

搜索方向因此变得清晰。

---

## 十四、形成 AlphaZero 式的迁移循环

整个迁移系统可以变成：

```text
                 Migration Agent
                        ↓
                  选择迁移任务
                        ↓
                    修改代码
                        ↓
              build / lint / test
                        ↓
                differential test
                        ↓
                     score
                        ↓
             ┌──────────┴─────────┐
             ↓                    ↓
           改善                  退化
             ↓                    ↓
        保留 candidate        回滚 candidate
             │
             └─────────┬──────────┘
                       ↓
                    再次尝试
                       ↓
                       ...
```

Git 是非常自然的状态管理器。

Worktree 则提供天然的并行探索环境：

```text
                 当前 migration state
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
      worktree A     worktree B     worktree C
          ↓              ↓              ↓
      strategy A     strategy B     strategy C
          ↓              ↓              ↓
        score 81       score 67       score 92
                                       ↓
                                     保留
```

这已经非常接近 evolutionary search。

---

## 十五、LLM 的作用：不是随机搜索，而是定向构造

OpenAI Five 需要巨量探索，因为它最初几乎不会玩 Dota。

Coding LLM 不同。

它可能直接判断：

> 旧框架中的这个 callback 生命周期与新框架不同，需要先引入 adapter，然后重新组织 ownership。

因此搜索过程是：

```text
               巨大候选空间
                    ↓
            LLM 的知识先验
                    ↓
          压缩为少数高概率方案
                    ↓
                Verifier
                    ↓
              真实环境筛选
```

这正是“大模型定向构造能力”的一个典型工程实例：

> **目标驱动 → 反向设计 → 候选构造 → 反馈收敛。**

LLM 不再只是一个“回答代码问题的模型”，而是成为搜索空间中的策略生成器。

---

## 十六、源代码迁移里的 Self-play：Self-generated Curriculum

严格来说，迁移不是双人对战，因此没有 Dota 式 self-play。

但可以构造一个等价机制：

> **让系统自动寻找当前 Agent 还不会迁移的东西。**

例如：

```text
简单 struct          ✓
普通函数             ✓
文件 IO              ✓
HTTP client          ✓
线程基础用法          ✓

复杂 callback        ✗
reflection           ✗
动态插件              ✗
并发状态机            ✗
复杂生命周期          ✗
```

系统就可以把探索逐渐集中在失败区域，自动形成 curriculum。

甚至可以加入一个 Adversarial Test Agent：

```text
Migration Agent
      ↓
生成迁移实现
      ↓
Adversarial Test Agent
      ↓
寻找能够破坏等价性的输入 / 状态
      ↓
发现 behavioral difference
      ↓
生成 regression case
      ↓
Migration Agent 修复
      ↓
Adversarial Agent 再攻击
      ↓
……
```

此时就出现了一种类似 self-play 的双边增强：

```text
迁移 Agent
    ↕
反例 / 测试 Agent
```

一个负责构造解决方案，另一个负责构造反例。

这与“定向构造能力”形成了漂亮的对偶：

- Migration Agent 定向构造满足约束的实现；
- Test Agent 定向构造能够击穿实现的反例。

二者共同推动系统边界不断扩大。

---

## 十七、失败必须永久成为环境的一部分

这一点可能是整个系统能否产生复利的关键。

错误的处理方式：

```text
Agent 做错
 ↓
找到 bug
 ↓
修好
 ↓
任务结束
```

正确的处理方式应该是：

```text
失败
 ↓
最小化失败案例
 ↓
保存成 regression test
 ↓
加入 migration benchmark
 ↓
以后所有 candidate 永久接受该测试
```

于是环境本身也在不断进化：

```text
Migration Environment V1
       ↓
发现 bug A
       ↓
Environment V2
       ↓
发现 bug B
       ↓
Environment V3
       ↓
发现 bug C
       ↓
Environment V4
```

这里发生了一个重要变化：

> **不仅 Agent 在进化，Verifier、测试集和环境本身也在进化。**

这与 OpenAI Five 中“对手随着自己一起增强”有很深的结构相似性。

---

## 十八、最终形成 Migration Benchmark

随着项目不断推进，可以自动积累出：

```text
migration_cases/
├── syntax/
├── api/
├── memory/
├── concurrency/
├── io/
├── network/
├── serialization/
├── error_handling/
├── lifecycle/
└── edge_cases/
```

每个 case 不只是文字说明，而是一组可执行知识：

```text
source implementation
+
input
+
expected old behavior
+
migrated implementation
+
assertions
+
historical failure traces
+
successful patch
```

几个月以后，系统获得的资产不只是一个迁移完成的软件项目，还包括：

> **一个针对这一类迁移问题的可执行知识库。**

传统知识可能只是：

> “迁移这里时注意线程安全。”

而可执行知识则是：

```text
这个具体输入
+
这个真实失败
+
这个 regression test
+
这个根因
+
这个正确 patch
```

它可以被机器持续复用，因此具有远高于普通文档的复利价值。

---

## 十九、第一阶段不要急着做真正的 RL

尽管整个讨论由 OpenAI Five / 强化学习引出，但工程上最合理的顺序并不是立即训练模型。

第一版可以只做：

```text
LLM
+
Search
+
Worktree
+
Tests
+
Differential Verifier
+
Trace
+
Memory
```

甚至最简单的 loop：

```text
generate → test → repair
```

就可能产生很强的效果。

一个基本系统可以是：

```text
while not migrated:

    选择下一个 module

    Agent 阅读：
        - 原代码
        - 目标架构
        - 历史经验

    Agent 生成 candidate

    verifier(candidate)

    if score improves:
        commit(candidate)
    else:
        rollback()

    将失败原因写入可执行知识库
```

此时已经拥有：

- state；
- action；
- environment；
- reward；
- search；
- memory。

只是还没有根据 trajectory 更新神经网络权重。

可以把它叫作：

### 第一阶段：Inference-time learning

```text
LLM 参数不变
Environment 变强
Verifier 变强
Memory 变强
Search 变强
```

等积累了足够多的：

```text
state
+
action
+
reward
+
trajectory
```

再进入：

### 第二阶段：Training-time learning

```text
trajectory
   ↓
SFT / RL / policy optimization
   ↓
更强的 migration policy
```

这样可以避免在 reward 尚不可靠时过早训练模型，导致 Agent 成功地优化一个错误指标。

## 二十、最终的软件迁移“生态系统”

完整系统可能长成：

```text
                    ┌────────────────┐
                    │ Migration Agent│
                    └───────┬────────┘
                            ↓
                  ┌──────────────────┐
                  │ Source Repository│
                  └────────┬─────────┘
                           ↓
                    产生 candidate
                           ↓
              ┌────────────────────────┐
              │   Sandbox / Worktree   │
              └────────────┬───────────┘
                           ↓
             ┌─────────────┼─────────────┐
             ↓             ↓             ↓
           build          test       benchmark
             │             │             │
             └─────────────┼─────────────┘
                           ↓
                       Verifier
                           ↓
                     reward / trace
                           ↓
               ┌───────────┴───────────┐
               ↓                       ↓
            Memory                  Search
               ↓                       ↓
        历史错误 / 规则            新 candidate
               └───────────┬───────────┘
                           ↓
                    Migration Agent
```

旁边还可以有：

```text
Adversarial Test Agent
          ↓
寻找新输入 / 边界条件
          ↓
攻击迁移后的实现
          ↓
发现 behavioral difference
          ↓
生成 regression test
          ↓
Verifier 变强
```

此时系统开始出现真正的生态性质：

- Migration Agent 在增强；
- Test Agent 在增强；
- Verifier 在增强；
- Test suite 在增强；
- Memory 在积累；
- 环境难度在提高；
- 项目迁移覆盖范围在扩大。

这与最开始讨论的自然生态系统重新闭环：

> 一个高度自治系统的关键不是与外界完全断开，而是内部形成足够完整的生产、消耗、反馈、选择、修复和记忆机制。

# 二十一、建议的实际实施路线

如果真正把这个思想用于源代码迁移项目，可以分五个阶段推进。

## 阶段 1：建立可判定环境

选择一个足够小的模块，使旧实现和新实现能够接受同一组输入，并对输出做自动差分。

目标不是“让 Agent 很聪明”，而是先做到：

> **系统可以可靠判断某一次迁移究竟好还是坏。**

## 阶段 2：建立 Agent 闭环

让 Codex / Claude / 其他 Coding Agent 自动完成：

```text
修改
 ↓
build
 ↓
test
 ↓
分析错误
 ↓
再次修改
```

暂时不做模型训练。

## 阶段 3：经验永久化

每一个真实失败都转化成：

- regression test；
- trace；
- 根因；
- 成功 patch；
- 新的 verifier 规则。

让线上失败成为永久知识。

## 阶段 4：并行搜索

一个迁移任务启动多个 worktree：

```text
Candidate A
Candidate B
Candidate C
...
```

由 verifier 自动评分，选择最优路径。

## 阶段 5：自主课程与训练

系统主动寻找当前能力最弱的迁移区域，自动构造边界条件和反例。

积累足够 trajectory 后，再研究：

- RL；
- SFT；
- policy optimization；
- evolutionary search；
- learned verifier；
- curriculum generation。

# 二十二、整场讨论最终收敛出的核心原则

今天的讨论可以浓缩为以下几条原则。

### 1. 不要首先训练一个“会迁移代码的 AI”，先构造一个 AI 可以无限练习迁移且每次都得到可靠反馈的世界

OpenAI Five 最值得借鉴的首先不是 PPO，而是它拥有一个可重复运行的 Dota 世界。

对应到软件工程：

> **先造 Source Migration World，再让 Agent 在里面变强。**

### 2. Verifier 的价值可能高于第一阶段的模型能力提升

如果不能准确判断 candidate 好坏，再强的 Agent 也无法稳定收敛。

因此：

> **环境和反馈质量决定了自主进化的上限。**

### 3. 失败必须永久进入系统

一次失败如果只是被修掉，就没有形成复利。

只有当它变成 regression case、benchmark 或 verifier 规则，系统才真正获得了长期记忆。

### 4. 环境也需要进化

真正的自我增强系统中，不仅 Agent 应该越来越强：

> **测试、验证器、任务难度、反例库、环境边界都应该同时增长。**

### 5. LLM 的核心价值是提供强搜索偏置

现代 LLM 使我们不再需要从随机行动开始探索软件工程空间。

它可以根据人类已有知识直接构造高概率候选，再由真实环境做选择。

因此它特别适合：

> **定向构造 + 自动验证 + 反馈收敛。**

### 6. 强大的系统往往来自连接创新，而不是单点创新

LLM、RL、Git、worktree、Docker、tests、Opik、tracing、memory、E2E、differential testing 单独看都不是魔法。

真正的突破可能来自：

> **找到这些方法之间的接口，把它们组织成一个能够自我增强的循环。**

---

# 二十三、最终的一句话

如果必须用一句话总结今天整场讨论：

> **未来高度自主的软件工程系统，可能不是一个单独“极其聪明”的大模型，而是一个以大模型为策略生成器、以可执行软件环境为世界、以测试和差分验证为选择压力、以搜索与强化学习为探索机制、以 trace 与 regression case 为长期记忆，并能在持续反馈中不断扩大能力边界的半封闭数字生态系统。**

或者用更简洁、更接近 OpenAI Five 的表达：

> **不要先问怎样造出一个会迁移整个项目的 AI；先问怎样造出一个 AI 可以永远练习源代码迁移、而且每一次尝试都会让整个系统变得更强的世界。**
