# 从聊天实验到 Agent 化：大模型产品方法论笔记

> 日期：2026-05-27  
> 状态：工作假设 / 方法论草稿  
> 目的：记录关于“大模型产品应该如何从真实问题中长出来”的阶段性认知。

## 1. 核心判断

不要一开始就急着写 `skill` 或 `agent`。

更稳妥的路径是：先和大模型进行大量真实对话，观察哪些问题在实践中真正有效；再分析这些问题为什么有效；等方法逐渐成熟后，再把它们封装成 `skill` 或 `agent`。

也就是说：

> 先用聊天探索问题空间，再抽象有效问题模式，最后才工程化成 agent。

`skill` 和 `agent` 不应该是探索未知问题的起点，而应该是成熟方法的结果。

## 2. 为什么不能太早 Agent 化

如果一开始就做 agent，实际上默认我们已经知道：

- 用户会提出什么问题；
- 哪些信息必须被收集；
- 判断标准是什么；
- 输出格式应该怎样；
- 哪些步骤可以自动化；
- 哪些地方必须保留人的判断。

但在早期，这些通常都还没有被验证。

过早 agent 化的风险是：

1. 把未经验证的问题理解固化成流程；
2. 把创始人或产品设计者的想象误认为用户真实需求；
3. 把“逻辑上合理”的方法误认为“实践中有效”的方法；
4. 让系统看起来更自动化，但实际削弱了人和模型共同探索问题的能力。

因此，早期更重要的不是自动化，而是理解问题。

## 3. Idea 不是事实，方法需要验证

一个 idea 听起来合理，并不代表它在真实场景中有效。

例如：

- “用户应该会需要这个”；
- “这个流程应该能提高效率”；
- “大模型应该能帮他们解决这个问题”；
- “只要做成 agent，体验应该会更好”。

这些都只是假设，不是事实。

我们不能主观地凭借自己的想象创造产品，而应该通过可控实验和数据反馈来判断一种方法是否有效。

核心原则：

> 不用主观想象创造产品，而是用可控实验发现有效问题和有效方法。

## 4. 把产品判断拆成可验证假设

更合理的表达方式不是：

> 我们要做一个 agent。

而是：

> 我们认为，在某类任务、某类用户、某类场景下，某种提问方式或工作流，会比普通聊天产生更好的结果。

这样，产品判断就可以被实验验证。

一个完整假设至少应该包含：

- 目标用户是谁；
- 具体任务是什么；
- 当前 baseline 是什么；
- 新方法改变了哪个变量；
- 预期提升体现在哪些指标上；
- 什么结果能证明假设不成立。

## 5. 控制变量实验设计

可以把不同方法放在同一类真实任务中比较。

### A. 普通聊天 Baseline

用户自由向模型提问，模型自由回答。

这是最重要的基线，因为任何新方法都必须证明自己比普通聊天更好。

### B. 结构化问题模板

给用户一个固定提问框架，例如：

- 背景；
- 目标；
- 约束；
- 已有材料；
- 判断标准；
- 期望输出。

验证问题：结构化输入是否让结果更稳定、更可用？

### C. 半自动工作流

模型主动进行：

- 澄清问题；
- 暴露假设；
- 总结上下文；
- 提出方案；
- 让用户确认关键判断。

验证问题：主动追问和阶段性总结是否降低用户认知负担？

### D. Agent 化流程

系统自动执行一部分步骤，例如：

- 检索资料；
- 比较方案；
- 生成文档；
- 调用工具；
- 检查输出质量；
- 根据规则迭代。

验证问题：自动化是否真的提高任务完成质量和效率，还是只是增加复杂度？

## 6. 评估指标

实验不应该只看主观感受，而应该尽量结合行为数据和结果质量。

可以观察：

- 用户是否更快得到可用结果；
- 结果是否更稳定；
- 用户是否减少返工；
- 用户是否更愿意继续使用；
- 是否降低用户的认知负担；
- 是否提升任务完成率；
- 是否比用户自己自由聊天更好；
- 用户是否愿意把这个流程用于下一次类似任务。

尤其要警惕一种情况：

> 用户觉得体验很高级，但实际任务结果并没有变好。

## 7. 有效问题本身就是产品资产

早期最值得研究的不是“做什么功能”，而是“什么问题能激发大模型产生高质量输出”。

需要观察的问题包括：

- 哪些问题能让模型暴露隐含假设；
- 哪些问题能让模型从现象上升到结构；
- 哪些问题能让模型给出可执行判断；
- 哪些问题能帮助用户重新定义问题；
- 哪些问题适合多轮追问；
- 哪些问题适合一次性结构化；
- 哪些问题看起来高级但在实践中没有帮助。

这些有效问题模式，后续可以沉淀为模板、协议、skill，最终才可能成为 agent。

## 8. 从聊天到 Agent 的成熟路径

可以把演化过程理解为四个阶段：

### 阶段 1：自由聊天

目标是探索问题空间，不追求流程稳定。

重点是记录：

- 用户真实怎么问；
- 哪些回答有用；
- 哪些回答无效；
- 用户在哪些地方继续追问；
- 哪些任务反复出现。

### 阶段 2：问题模式识别

从真实对话中抽象出高频、有效的问题模式。

例如：

- 诊断型问题；
- 比较型问题；
- 规划型问题；
- 评估型问题；
- 反思型问题；
- 决策型问题。

### 阶段 3：方法协议化

把有效模式整理成可复用的工作流。

此时可以出现：

- prompt 模板；
- 检查清单；
- 输入字段；
- 输出结构；
- 质量判断标准。

### 阶段 4：Skill / Agent 化

只有当某个工作流已经反复验证有效，边界也比较清楚时，才值得封装成 skill 或 agent。

判断标准包括：

- 任务类型稳定；
- 输入信息结构稳定；
- 中间步骤稳定；
- 质量标准稳定；
- 失败模式可以被识别；
- 自动化确实优于人工聊天。

## 9. 关键原则

### 原则一：Agent 不应该先于方法论出现

`skill` 是成熟问题处理方式的封装。  
`agent` 是成熟工作流的自动化。  
它们都不应该是产品探索的起点。

### 原则二：先验证问题，再验证方法，最后验证产品形态

顺序应该是：

1. 这个问题是否真实存在；
2. 大模型是否能在这个问题上提供独特价值；
3. 哪种提问方式或工作流最有效；
4. 这种方法是否值得产品化；
5. 是否需要 agent 化。

### 原则三：把失败样本当成资产

失败对话很重要，因为它们能暴露：

- 用户真实意图不清晰；
- 模型容易误解的地方；
- 当前流程缺少的信息；
- 自动化不应该介入的环节；
- 需要保留人类判断的边界。

### 原则四：数据回应想象

产品直觉可以提出假设，但不能替代验证。

最终应该由真实对话、真实任务、真实用户反馈和可比较的数据来回应：

> 这个方法到底有没有用？

## 10. 下一步行动

接下来可以建立一个“认知实验场”：

1. 收集真实用户与大模型的对话；
2. 标注哪些问题产生了高质量结果；
3. 分析有效问题背后的结构；
4. 把问题模式分类；
5. 设计对照实验；
6. 比较普通聊天、结构化模板、半自动流程和 agent 化流程；
7. 用结果决定是否产品化；
8. 只把被反复验证的方法沉淀为 skill 或 agent。

## 11. 当前工作假设

目前的工作假设是：

> 大模型产品的早期核心不是构建 agent，而是发现“哪些问题在大模型环境下真正有效”。

进一步说：

> 产品不是从想象中的功能开始，而是从被实验验证过的问题和方法中长出来。
